## 1. 목표

숙박 커머스 백엔드에 **숙소 검색 → 객실 타입 선택 → 예약 생성 → 일자별 재고 차감 → 결제 → 확정**으로 이어지는 핵심 흐름을 구축한다. 동시성 문제로 인한 더블부킹을 구조적으로 차단하고, 외부 결제 시스템의 성공/실패와 예약/재고 상태를 일관되게 유지한다.

## 2. 원본 요구사항 (Quest)

### 유저 스토리

이 도메인이 풀어주는 사용자 경험을 한 문단으로 그려둔다. 코드·테이블·시퀀스를 모두 빼고 읽어도 이해되어야 한다.

- **게스트로서**, 가고 싶은 **도시**와 **묵을 날짜**, 함께 갈 **인원수**를 입력해 묵을 수 있는 숙소들을 한눈에 비교하고 싶다.
- **게스트로서**, 검색 결과에서 **총 얼마 드는지**와 **하루 평균 얼마인지**를 같이 보고 의사결정하고 싶다.
- **게스트로서**, 원하는 **객실 타입**을 골라 예약을 시작하면, 결제하는 동안 **다른 사람이 내 방을 채가지 못하기**를 기대한다.
- **게스트로서**, 결제에 실패하거나 결제 페이지를 닫으면 **재고가 자동으로 풀려** 다른 사용자가 시도할 수 있어야 한다.
- **게스트로서**, 마음에 드는 숙소를 **찜**해두고 나중에 다시 확인하고 싶다.
- **게스트로서**, 예약 상태(대기 / 확정 / 체크인 / 체크아웃 / 취소 / 노쇼)가 지금 어디인지를 명확히 알고 싶다.

### 기능 흐름 (Main / Alternate / Exception Flow)

비개발자가 "이 기능이 어떤 단계로 흘러가는가"를 따라갈 수 있도록 핵심 시나리오를 풀어둔다.

**A. 검색 → 예약 생성 → 결제 — 정상 흐름 (Main Flow)**

1. 게스트가 도시·체크인·체크아웃·인원수를 입력해 검색한다.
2. 시스템은 해당 도시의 숙소 중 인원을 수용 가능한 객실 타입을 찾는다.
3. 검색 기간의 **모든 일자에 재고가 남아 있는** 객실만 결과에 포함한다.
4. 각 결과의 **합산 가격**과 **1박 평균 가격**을 함께 보여준다.
5. 게스트가 객실 타입을 선택하면 시스템은 결제 대기(PENDING) 상태로 예약을 만든다.
6. **이 순간 해당 기간의 모든 일자에서 객실 1개가 차감된다 (소프트 홀드, 10분).**
7. 게스트가 외부 결제(PG)에서 결제를 완료한다.
8. 결제 성공 콜백이 도착하면 예약은 **CONFIRMED**가 된다.

**B. 결제 실패 / 만료 — 대체 흐름 (Alternate Flow)**

- B-1. 게스트가 결제 페이지를 닫고 돌아오지 않으면, 10분 뒤 백그라운드 스케줄러가 예약을 **자동 CANCELLED**로 바꾸고 재고를 되돌린다.
- B-2. 결제 실패 콜백이 도착하면 즉시 **CANCELLED + 재고 복구**가 이루어진다.
- B-3. 게스트가 만료된 결제 페이지로 돌아와 결제를 시도하면 "예약이 만료되었습니다" 안내와 함께 다시 예약하도록 유도한다.

**C. 동시성 충돌 — 예외 흐름 (Exception Flow)**

- C-1. 같은 객실 타입의 마지막 1개를 두 게스트가 거의 동시에 예약 시도한다.
- C-2. 시스템은 **DB 차원에서 한 명만 차감에 성공**시키고 다른 한 명에게는 "재고 부족" 안내를 보낸다.
- C-3. 결제 도중 호스트가 가격을 변경하더라도, 결제 진행 중인 게스트에게는 **예약 시작 시점의 가격**이 그대로 청구된다.

**D. 취소 — 게스트 주도 (Alternate Flow)**

- D-1. 게스트가 PENDING 또는 CONFIRMED 상태에서 취소를 요청한다.
- D-2. 시스템은 예약을 **CANCELLED**로 바꾸고 재고를 되돌린다.
- D-3. 체크인이 시작된 이후에는 시스템 차원에서 취소가 불가능하며 운영 채널을 통해서만 처리한다.
- D-4. 취소 시 **환불 산정·실행은 별도 도메인(후속 라운드)이 담당**한다. 이번 라운드는 "취소되었다"는 사실을 이벤트로 알린다.

### 기능 요구사항
- 사용자는 **도시/체크인/체크아웃/인원수**로 숙소를 검색한다.
- 검색 결과에는 해당 기간의 **합산 가격**과 **1박 평균 가격**을 함께 표시한다.
- 사용자는 **객실 타입**을 선택해 예약을 생성한다.
- 예약 시 **일자별 재고가 차감**되고, **더블부킹은 발생하면 안 된다**.

### 유비쿼터스 언어 (Ubiquitous Language)

기획·디자인·개발·QA가 같은 단어로 같은 개념을 가리킬 수 있도록 도메인 용어를 고정한다. 이 표가 곧 코드의 클래스명·테이블명·API 응답 필드명의 기준이 된다.

| 한국어 | 영문 (코드·테이블 기준) | 정의 |
|--------|------------------------|------|
| 숙소 | **Property** | 호텔/펜션/모텔/리조트 단위의 판매 단위. 호스트가 운영한다. |
| 객실 타입 | **RoomType** | 한 숙소가 판매하는 객실 카테고리 (예: 스탠다드 더블). 최대 수용 인원·침대 타입 보유. |
| 일자별 재고 | **DailyRoomInventory** | 특정 (객실 타입, 날짜)의 잔여 객실 수량. |
| 일자별 요금 | **DailyRoomRate** | 특정 (객실 타입, 날짜)의 1박 요금. |
| 예약 | **Reservation** | 게스트의 객실 점유 계약. 상태 머신을 보유. |
| 예약 일자 스냅샷 | **ReservationNightly** | 예약 1건의 일자별 가격 스냅샷 (환불 산정의 기반). |
| 찜 | **Wishlist** | 게스트가 숙소를 즐겨찾기한 기록. |
| 게스트 | **Guest** | 검색·예약·결제를 수행하는 회원. (commerce-user 도메인의 USER) |
| 호스트 | **Host** | 숙소·객실·재고를 등록·운영하는 회원. (commerce-user 도메인의 USER) |
| 결제 대기 (소프트 홀드) | **PENDING** | 결제 전 10분간 재고를 점유한 상태. |
| 확정 | **CONFIRMED** | 결제 성공으로 점유가 확정된 상태. |
| 체크인 | **CHECKED_IN** | 게스트가 입실한 상태. |
| 체크아웃 | **CHECKED_OUT** | 퇴실 완료 (스케줄러 자동 전이). |
| 취소 | **CANCELLED** | 만료·결제 실패·사용자 요청으로 종료된 상태. |
| 노쇼 | **NO_SHOW** | 체크인일에 입실하지 않아 종료된 상태. |
| 결제 시스템 | **PaymentGateway (PG)** | 외부 결제 서비스. webhook으로 성공/실패를 통지. |
| 인벤토리 서비스 | **InventoryService** | 일자별 재고 차감/복구 단독 책임자. |

> **금지어**: "방", "객실", "타입", "아이템", "상품" 같은 모호한 호칭은 코드·문서에서 사용하지 않는다. 항상 위 표의 정의된 용어를 쓴다.

### 제안사항
- 일자별 재고는 `(room_type_id, date)` 단위 적재
- 예약 상태는 `PENDING → CONFIRMED → CHECKED_IN/CHECKED_OUT → CANCELLED` 흐름

### 도메인 범위
- **포함**: 숙소(Property), 객실 타입(RoomType), 일자별 재고(DailyRoomInventory), 일자별 요금(DailyRoomRate), 찜(Wishlist), 예약(Reservation)
- **제외**: 회원(commerce-user 도메인 — 1주차에서 완성)

## 3. 문제 상황 재해석

| 요구사항 | 사용자 관점 | 비즈니스 관점 | 시스템 관점 |
|---------|-------------|---------------|-------------|
| 검색 (도시/기간/인원) | 가고 싶은 도시·날짜에 일행이 묵을 수 있는 곳을 한눈에 비교 | 전환율의 출발점. 가격 표시 방식이 의사결정에 큰 영향 | N박 기간에 대한 N개 일자 요금 합산. 응답 시간 vs 가격 신선도 |
| 예약 생성 | 본 가격·본 객실을 그대로 점유하고 싶음 | 매출 실현 시점이 어디에서 확정되는가 | 동시 요청 중 한 명만 같은 (room_type, date)를 차지 |
| 재고 + 더블부킹 방지 | 다른 사용자가 동시에 같은 방을 못 예약해야 함 | 더블부킹 = 환불·재배정·평판 타격 | 동시성 제어 위치 — DB UNIQUE / Lock / 분산 락 |
| 상태 머신 | 내 예약 단계를 명확히 알고 싶음 | 각 상태가 환불·취소·노쇼 정책의 trigger | 비역전 invariant 보장 (예: CHECKED_OUT → PENDING 금지) |

### 재해석된 핵심 문제

> "검색 시점에 본 가격·재고로 예약을 시작했을 때, 결제·확정 사이 어딘가에서 동시성·외부 시스템 실패가 발생해도 **예약·재고·결제 3자가 어긋나지 않게 일관성을 유지하는 것**"

## 4. 합의된 결정사항

### [P3] 결제 흐름 — 소프트 홀드 모델 (선택지 A)

```
PENDING (재고 소프트 홀드)
  ├─ 결제 성공 → CONFIRMED
  └─ 결제 실패 / 타임아웃 → 자동 CANCELLED + 재고 복구
```

- 예약 생성 시점에 일자별 재고를 즉시 점유하되, **소프트 홀드(PENDING)** 로 표시한다.
- 결제 시스템 호출이 성공하면 `CONFIRMED`로 전이.
- 결제 실패·타임아웃 시 시스템이 PENDING을 `CANCELLED`로 전이하고 재고를 반환한다.

**근거**: 결제 중 다른 사용자가 같은 객실을 채가는 경험 차단. 결제·재고 결과의 일관성은 보상 트랜잭션 없이 상태 전이로 해결.

### [B1] 일자별 재고 차감 책임 — InventoryService 단독 (선택지 A)

- `Reservation` 도메인은 재고 테이블을 직접 만지지 않는다.
- 전용 `InventoryService.reserve(roomTypeId, dates)` / `.release(...)` 인터페이스를 호출한다.

**근거**:
- 동시성 제어 로직(락·낙관락·UNIQUE)을 한 곳에 응집 → 테스트 용이.
- 추후 캐시 도입·분산 락 도입 시 변경 격리.
- `Reservation`은 "예약이 어떤 상태에 있는가"에만 집중.

### [P4] PENDING 만료·복구 — 10분 소프트 홀드 (선택지 A)

- PENDING 생성 시 만료 시각(`expiresAt`)을 함께 기록한다 (`createdAt + 10분`).
- 만료된 PENDING은:
  1. 사용자 결제 시도 시 → `EXPIRED` 응답
  2. 백그라운드 스케줄러 / 만료 이벤트 → `CANCELLED` 전이 + `InventoryService.release` 호출
- TTL 저장소(Redis)와 RDB의 정합성을 어떻게 보장할지는 설계 단계에서 결정 (B5와 연결).

**근거**: 사용자 결제 시간(외부 PG 리다이렉트 포함) 확보와 재고 회전율의 균형. 10분은 일반적 상용 서비스 표준.

### [B2] 가격 잠금 시점 — PENDING 스냅샷 (선택지 A)

- `Reservation`은 PENDING 생성 시점의 일자별 요금을 **스냅샷**으로 보유한다 (`totalAmount`, `nightlyBreakdown`).
- 결제·취소·확정 전 과정에서 이 스냅샷을 진실값으로 사용한다.
- 검색에서 본 가격과 PENDING 생성 사이에 가격이 변하면 → 사용자에게 변동 안내 후 재확인 (이번 라운드는 단순화: 변동 안내 메시지만 정의, 재확인 플로우는 후속).

**근거**: 결제 도중 가격이 바뀌어 사용자에게 다른 금액이 청구되는 경험 차단. 가격 변동 시 시스템 책임이 명확해짐.

### [B4] 호실 식별성 — RoomInstance 없음 (선택지 A)

- `DailyRoomInventory`는 `(room_type_id, date, remaining)` 형태로 **수량만** 관리한다.
- 사용자는 "201호" 같은 특정 호실을 지정할 수 없다. 운영자는 체크인 시점에 호실을 배정한다고 가정.
- "remaining > 0"이 곧 "예약 가능" — 더블부킹 방지는 `remaining = 0`으로 만드는 원자적 차감으로 보장.

**근거**: 이번 라운드 범위(설계 기반 구축)에 집중. 호실 단위 식별이 필요해지면 별도 도메인(`RoomInstance`)으로 확장.

### [P1] 인원수 처리 — maxOccupancy 필터 (선택지 A)

- 검색 조건의 `guestCount`는 `RoomType.maxOccupancy >= guestCount` 필터로 적용한다.
- 한 객실에 일행 전원이 머문다고 가정. 다중 객실 조합 검색은 이번 라운드 범위 외 (E1).

### [P5] 취소 정책 — 트리거·상태만 (선택지 A)

- 이번 라운드는 **취소 가능 여부**와 **재고 복구** 흐름만 설계한다.
- 위약금 계산·환불액 산정은 후속 라운드 (`CancellationPolicy` 도메인으로 분리 예정).
- 취소 가능 조건: PENDING(자동/수동), CONFIRMED(수동), CHECKED_IN 이후 불가.

### [P2] 가격 표시 범위 — 객실요금만 (선택지 A)

- 표시·합산 가격은 `DailyRoomRate.amount`의 N일 합 = `Reservation.totalAmount`이다.
- 세금·수수료는 이번 라운드 설계 모델에 포함하지 않으며, 후속 라운드의 `TaxFeePolicy`로 분리한다.

### [P6] 노쇼 처리 — 별도 `NO_SHOW` 상태 (선택지 A)

- `CONFIRMED` 상태에서 체크인일 종료 시각까지 `CHECKED_IN` 전이가 없으면 스케줄러가 `NO_SHOW`로 전이한다.
- 노쇼는 정산·통계·환불 정책에서 일반 `CANCELLED`와 구분된다.

### [P7] 체크아웃 전이 — 스케줄러 자동 (선택지 A)

- 체크아웃일 익일 특정 시각(예: 11:00 KST)에 `CHECKED_IN → CHECKED_OUT` 자동 전이.
- 호스트의 수동 전이도 허용하되 이번 라운드 시퀀스에는 자동 전이만 명시.

### [P8] 1박 평균 — 단순평균 (선택지 A)

- `avgNightlyPrice = totalAmount / nights`
- 평일·주말 구분 표시는 후속 라운드 (E2와 함께 가변 가격 모델 도입 시).

### [B3] RoomType ↔ Property — 1:N 고정

- `Property 1 ─── N RoomType` 관계를 ERD·클래스 모델 모두에 명시.
- 동일 `RoomType` 인스턴스가 여러 `Property`에 속하는 케이스는 없다.

## 7. 액터 (잠정)

- **게스트(Guest)**: 검색 → 예약 → 결제 → 체크인/아웃 진행
- **호스트(Host)**: 숙소·객실 타입·일자별 재고·요금 등록 *(이번 라운드 설계에선 사전 데이터 가정 가능)*
- **결제 시스템(PG)**: 외부. CONFIRMED 전이의 trigger
- **스케줄러**: PENDING 만료·자동 체크아웃 등 시간 기반 전이
