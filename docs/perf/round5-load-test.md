# Round 5 — 검색 API 부하 테스트 (k6)

단일 쿼리 벤치마크(`round5-search-optimization.md`)에 이어, 실제 HTTP 경로(Tomcat → 캐시 → DB)의 동시성 한계를 측정한다.
스크립트: `docs/perf/load/search-load.js` (실행 전제·명령은 스크립트 상단 주석 참조).

## 1. 시나리오

| 시나리오 | 트래픽 성격 | 부하 | 구성 |
|----------|-------------|------|------|
| hot | 인기 검색 반복 — 캐시 키 12개(조합 4 × 정렬 3), TTL 60초 내 재사용 → 캐시 적중 위주 | 0→100 VU 램프 후 60초 유지 | 검색 80% + 상세 20% |
| cold | 롱테일 — 도시·날짜·인원·정렬·페이지 전부 랜덤 → 사실상 전부 캐시 미스(DB 직행) | 0→40 VU 램프 후 60초 유지 | 검색 80% + 상세 20% |

환경: 로컬 단일 인스턴스(Tomcat 스레드 200, Hikari 풀 40), MySQL 8.0·Redis 7.0 docker, 시드 = 벤치마크와 동일(숙소 1만 / daily 각 615만 행). k6도 같은 머신에서 실행 — 절대값보다 두 경로의 상대 비교가 목적이다.

## 2. 결과

| 지표 | hot (캐시 적중) | cold (캐시 미스) |
|------|----------------|------------------|
| 처리량 | **≈ 2,485 RPS** (721,057건 / 2m20s) | **≈ 21 RPS** (2,697건 / 활성 2m10s) |
| 응답 시간 | med 7.7ms / p95 **31.5ms** | med 1.08s / p95 **4.2s** |
| 실패율 | 0.02% (203건 — 아래 § 3) | 0% |

- 캐시 적중 경로와 미스 경로의 처리량 차이는 **약 120배**. 인덱스 최적화 후에도 남는 검색 본질 비용(일자별 조인·집계, 단일 쿼리 ~130ms)이 동시성 한계를 그대로 결정한다 — 40 VU만으로 DB가 포화되어 응답이 초 단위로 밀린다.
- 즉 이 시스템의 실질 수용량은 "캐시 적중률"이 결정한다. 인기 검색 위주 트래픽이면 단일 인스턴스로 2,000+ RPS, 롱테일 위주면 ~20 RPS.

## 3. 발견 — 캐시 스탬피드 (TTL 동시 만료)

hot 시나리오의 실패 203건은 전부 `CannotCreateTransactionException` — Hikari 풀 고갈(`total=40, active=40, waiting=57`, 3초 대기 타임아웃 → 500)이다. 발생 시각이 **13:30:25와 13:31:34, 정확히 60초 간격 = 검색 캐시 TTL 경계**에 몰려 있다.

메커니즘: 테스트 시작 시 12개 캐시 키가 거의 동시에 적재되고, 60초 뒤 **동시에 만료**된다. 만료 순간 100 VU 전원이 미스 → 미스마다 DB 직행(단일 비행 없음) → 커넥션 40개 고갈 → 대기 3초 초과분은 500. 캐시 재적재가 끝나면 즉시 정상화되어 초 단위 스파이크로 끝나지만, 트래픽이 클수록·쿼리가 무거울수록 스파이크가 길어진다.

### 개선 후보 (미구현)

| 방법 | 내용 | 트레이드오프 |
|------|------|--------------|
| TTL 지터 | TTL을 60s ± 랜덤 10s로 분산해 동시 만료 제거 | 구현 한 줄, 효과는 완화(만료 순간 herd 자체는 남음) |
| 단일 비행(single-flight) | 미스 시 키당 1개 요청만 DB 조회, 나머지는 대기/이전 값 | 분산 락(Redis SET NX) 필요, 지연 추가 |
| stale-while-revalidate | 만료 후에도 이전 값을 서빙하며 백그라운드 갱신 | 신선도 저하 허용 필요(검색은 이미 60초 낡음 허용이므로 적합) |

권장 조합: **TTL 지터(즉시) + stale-while-revalidate(후속)**. 검색 결과는 이미 "낡아도 결제 시점 DB 재확인으로 안전"한 설계(`wiki/accommodation/design-decisions.md#search-cache`)라서 신선도 트레이드오프 부담이 없다.

```bash
# 시드 후, 앱을 시드 보존 모드로 기동 (ddl-auto=create 무력화 + SQL 로그 끔)
./gradlew :apps:commerce-api:bootRun --args='--spring.profiles.active=local,seed'
./gradlew :apps:commerce-api:bootRun --args='--spring.profiles.active=local --spring.jpa.hibernate.ddl-auto=none --spring.jpa.show-sql=false'

k6 run docs/perf/load/search-load.js
```
